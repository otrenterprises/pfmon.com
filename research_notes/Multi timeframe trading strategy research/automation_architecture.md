## 1. Architecture for an event-driven signal engine (tick ingestion → bar builders → feature layers → setup state machines → order manager → risk manager → journal), state machines, idempotency, restart recovery, session handling, rollover

### Takeaway
Build one deterministic, single-writer core that handles an ordered event stream (ticks, bar closes, order/fill notifications, timers). Everything downstream of ticks should be a pure function of that stream, so any trigger can be replayed and audited exactly. Each setup gets an explicit state machine whose ID is derived from the level and bar that created it. Restart is always "reconcile with the broker first, then re-arm". The repo's existing Rithmic layer is a browser-based connection/decoding test harness. It has a fixed 30 s heartbeat and no reconnect logic, so it has to be hardened or moved server-side before any unattended order routing.

### Inferences
**Recommended layered pipeline** (one process, one event loop for the decision core, I/O adapters on the edges):
1. **Adapters (I/O only):** Rithmic TICKER/HISTORY/ORDER/PNL plant connections and/or Tradovate md + trading WebSockets. Normalize everything into internal events `{seq, recv_ts, exch_ts, source, type, payload}`. Drop or flag `isSnapshot=true` LastTrade/BBO messages so snapshots are not double-counted as trades.
2. **Event log (append-only, durable):** write every normalized event before processing it (JSONL or SQLite WAL on disk, not browser downloads). This one log is the source for deterministic replay, the visual audit, and journal ingestion into pfmon.
3. **Bar builders** (pure functions of ticks): time bars at, e.g., 1m/5m/15m/30m/60m/240m/daily/weekly, aligned to the CME trade date (the day starts 17:00 CT on the prior calendar day, the week starts Sunday 17:00 CT). Volume bars at several sizes (e.g., ES 1,000/2,500/5,000 contracts). Each bar emits `BarClosed{tf, open_ts, close_ts, ohlcv, bid_vol, ask_vol, bar_id}` exactly once, plus optional `BarUpdated` for the developing bar. Decide explicitly whether a volume bar splits the boundary-crossing trade or overshoots, and keep that rule identical in live and replay.
4. **Feature layers** (each subscribes to specific bar streams and emits versioned outputs): swing detector (confirmed pivots only, with `pivot_time` and `confirm_time`), profile builder (developing and final session/weekly profiles: POC/VAH/VAL/HVN/LVN), Fib grid/cluster builder (anchored to confirmed swings, with re-anchor events), and a **level registry**. The registry holds every actionable level with a stable `level_id`, provenance (which feature, which anchors, which timeframe), creation time, and invalidation rules.
5. **Setup state machines** (one instance per candidate setup): `IDLE → ARMED → ORDER_PENDING → IN_POSITION → MANAGED → CLOSED`, plus terminal `EXPIRED / INVALIDATED / REJECTED / CANCELLED / ERROR`. Transitions only happen on explicit events (bar close, fill notification, timer, risk veto). Persist every transition with the triggering event's `seq`.
6. **Risk manager** (pre-trade veto plus continuous monitoring) sits between setups and the order manager. Nothing reaches the broker without passing it.
7. **Order manager:** maps an intent (`EnterLong setup_id=…`) to broker messages and tracks broker order state separately from setup state. The order manager is the only component allowed to talk to the order plant.
8. **Journal/logging:** decision records (see §3), order/fill events, and P&L, fed into the pfmon journal.

**Idempotency:** derive `setup_id = hash(strategy_version, setup_type, level_id, arming_bar_id)` and use it (or a short form) as Rithmic `userTag` / Tradovate `clOrdId` / strategy `uuid`. Before sending any order, check the persisted state and the broker's working orders for that tag. Sending only happens on a state transition, never "on every tick while condition true". Duplicate deliveries of the same event (e.g., a reconnect re-snapshot) must be no-ops.

**Restart recovery:** on start, (a) load persisted setup states, (b) query the broker (Rithmic `RequestShowOrders` + `RequestShowBrackets` + `RequestPnLPositionSnapshot` + `RequestReplayExecutions`; Tradovate `user/syncrequest`, which returns orders/positions/fills), (c) reconcile. A known tag with a matching broker state resumes management. A broker position or order with no known tag is "orphaned": alert the user and either adopt it under protective-only management or flatten (the policy must be chosen in advance). A local state with no broker counterpart is marked `ERROR` and never re-sent automatically. (d) Rebuild features from history (see §2), then resume. Never re-arm setups whose arming bar closed while the engine was down unless the rules explicitly allow late arming.

**Session rules to encode:** trade-date boundary 17:00 CT; no new entries during 16:00–17:00 CT maintenance, and no entries in the last N minutes before it (resting brackets' behavior across the break must be confirmed with the broker). Separate RTH (equity-index convention: 08:30–15:00 CT, matching the NYSE 09:30–16:00 ET cash session) from ETH profiles and swings. Load a holiday table and treat early-close days as short sessions. Use `MarketMode` halts (Rithmic) as hard "no new orders" signals.

**Rollover:** run a roll calendar (Monday-before-third-Friday per CME's stated convention, plus a volume-crossover check) and switch the traded symbol via `FrontMonthContractUpdate` / `rollcontract`. For multi-week features that span a roll, use a **back-adjusted (difference-adjusted)** continuous series so point distances (swing sizes, Fib ratios, ATR) are preserved, then translate the levels back into the new contract by adding the roll spread at the switch time. Profiles built on the old contract should either be shifted by the same spread or flagged "pre-roll" with reduced weight. Log the spread used.

**Browser hosting is unsuitable for unattended trading:** the current harness runs in a browser tab, and background tabs commonly throttle timers. Its heartbeat is fixed rather than server-specified, it has no reconnect, and it logs through file downloads. Move the engine to a headless Node (or similar) service. The repo's protos.json and proto-factory can probably be reused there.

### Gaps
- Exact Rithmic semantics for volume-bar boundary handling (does a trade that crosses the threshold split?) are not documented in the repo's Reference Guide. Verify empirically by comparing server `TickBar` volume bars against bars built from `LastTrade`.
- Whether Rithmic and Tradovate keep resting GTC/DAY orders and server-side brackets across the 16:00–17:00 CT maintenance break or the weekly close was not confirmed from official docs.
- CME's roll-dates page and official holiday calendar could not be fetched (HTTP 503 / not retrieved). Roll and holiday dates above rely partly on secondary sources.

## 2. Data: what the repo's Rithmic protos and Tradovate API actually expose (ticks, BBO, time/tick/volume bars, volume profile, history replay) and what is needed to seed weekly profiles and swing structure

### Takeaway
Rithmic's R|Protocol, as defined in the repo, covers essentially everything this strategy family needs. It provides aggressor-tagged tick trades, BBO, depth-by-order, server-built time bars (second/minute/daily/weekly), server-built tick, range and volume bars, a per-minute volume-profile history (`RequestVolumeProfileMinuteBars`, 208/209) that can be summed into session, weekly or monthly profiles, and a session volume-at-price snapshot. Tradovate's WebSocket market data provides quotes, DOM, a daily histogram (volume profile), and `md/getChart` with Tick, MinuteBar, DailyBar and Volume/Range bar units plus up/down and bid/offer volume. Neither API exposes a native monthly bar, and Tradovate has no weekly chart unit, so higher timeframes have to be built from daily bars.

### Inferences
- **Preferred data source for this strategy:** Rithmic, because it supplies aggressor-side ticks (needed for bid/ask-volume profiles and for the volume-bar builder), server-side volume bars for cross-checking, and minute-resolution profile history for seeding. Tradovate is a workable second path (its chart API supports `elementSizeUnit:"Volume"` and `withHistogram`), but its histogram is per trade date and it has no weekly unit.
- **Build bars locally from `LastTrade`** for live signals (full control over boundaries, sessions and the developing-bar state), and use server `TimeBar`/`TickBar` subscriptions as an independent consistency check. Alert if a local bar differs from the server bar by more than a tolerance. This also serves as FIA's "market data reasonability check" (see §5).
- **Seeding at startup (one-week cap):** request `WEEKLY_BAR` replay for 1–2 years (weekly swing structure), `DAILY_BAR` for 1–2 years (daily swings; monthly bars built from daily if wanted), `MINUTE_BAR` for 4–8 weeks (intraday swing structure across the 1m–240m timeframes), and `VOLUME_BAR` replays at each configured size for enough bars to confirm the swings. For profiles, sum `ResponseVolumeProfileMinuteBars` across the session (daily profile), Sunday 17:00 CT–Friday 16:00 CT (weekly), and the prior N weeks (composite). At roughly 1,380 minute bars per 23-hour Globex day, a week is about 6,900 bars and a month about 30,000, which is above the "round number such as 10000" truncation hint. Paginate by time window and verify continuity (no missing minutes outside the maintenance break).
- **History gap for tick-level features:** historical raw ticks are not exposed as such. If tick-level historical features are needed (e.g., to rebuild exact volume bars for past weeks), request 1-tick `TICK_BAR` replay, assuming `barTypeSpecifier "1"` is accepted (unverified), or rely on server `VOLUME_BAR` replay. Otherwise, record ticks continuously from day one so the engine's own archive becomes the replay source.
- **Use `OrderPriceLimits` (163) and `MarketMode` (157)** as inputs to pre-trade checks (price within limits, market open, not halted).
- **Tradovate tick packets can arrive out of order:** sort by tick `id` and timestamp before feeding bar builders, and never process ticks from history and real time interleaved without dedup by `id`.
- **Tradovate's one-connection default** means a desktop Tradovate/NinjaTrader session and the bot cannot run simultaneously on the same user without a paid extra connection. The oldest connection gets dropped, which in automation means a silent loss of order monitoring.

## 3. Avoiding look-ahead and repainting in live signals; logging what was known at signal time for visual audit

### Takeaway
Every feature must be defined in terms of information that existed at decision time. That means swings confirmed only after their confirmation window closes, higher-timeframe values taken from the last closed bar (or an explicitly labelled developing bar), profiles labelled "developing" or "final", and Fib grids versioned with their anchors. Each trigger should write an immutable "decision record" containing the exact inputs and a pointer to the event-log sequence number, so the user's visual review compares the chart against what the engine actually saw rather than the repainted hindsight view.

### Cited Findings
- TradingView's Pine docs say `request.security()` "only returns confirmed values from its requested context on historical bars, whereas it can return unconfirmed values on realtime bars". The documented non-repainting pattern offsets the expression with `[1]` and sets `lookahead = barmerge.lookahead_on`. — [TradingView Pine Script docs: Repainting](https://br.tradingview.com/pine-script-docs/en/v5/concepts/Repainting.html)
- PineCoders: if a system relies on alerts, "the simplest solution is to configure alerts to trigger Once Per Bar Close". A 2025 third-party guide recommends `lookahead_off` with gating on confirmed HTF bars instead. These are different approaches, and the second is only safe with explicit confirmation gating. — [PineCoders FAQ: How to avoid repainting when using security()](https://kr.tradingview.com/script/cyPWY96u-How-to-avoid-repainting-when-using-security-PineCoders-FAQ/); [Pine v6 alerts guide (third-party)](https://pinescripter.vercel.app/blogs/pine-script-v6-alerts-guide-alertcondition-alert)
- NinjaTrader: "State.Historical data processes OnBarUpdate() only on the close of each historical bar even if this property is set to OnEachTick or OnPriceChange". Tick Replay exists to "play back 1 tick historical data to build the bars as if they had been build live" but "was NOT designed to provide accuracy in backtesting concerning order fills and execution." — [NinjaTrader: Developing for Tick Replay](https://static.ninjatrader.com/support/helpGuides/nt8/developing_for__tick_replay.htm); [NinjaTrader: Calculate](https://ninjatrader-live.ninjatrader.com/support/helpguides/nt8/calculate.htm)
- NinjaTrader multi-series: in real time, with multiple same-instrument series and a trading-hours template, "Any ticks not processed will be queued and processed as a tick comes in for all subsequent DataSeries". This means processing order across timeframes is a platform behavior that has to be understood. — [NinjaTrader AddDataSeries()](https://static.ninjatrader.com/support/helpGuides/nt8/adddataseries.htm)
- Sierra Chart ACSIL: order actions "do not occur on historical bars or while historical data is being downloaded". Full recalculations return `SCT_SKIPPED_FULL_RECALC`. Fill markers may appear on later bars than the triggering bar, so the Trade Activity Log's "Bar start date-time" is the reliable check. — [Sierra Chart: ACSIL Trading](https://www.sierrachart.com/index.php?page=doc/ACSILTrading.html)
- FIA recommends checks that "validate whether actionable data is reasonable based on… the time since the last update was received, previous price, bid/offer spread or deviation from an average price", with orders "blocked while the deviation is investigated". — [FIA, Best Practices for Automated Trading Risk Controls and System Safeguards (July 2024), §3.1](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)
- Rithmic timestamps: `LastTrade` carries exchange-source time (`sourceSsboe/sourceUsecs/sourceNsecs`), the gateway receive time (`ssboe/usecs`), and `jopSsboe/jopNsecs`. `ExchangeOrderNotification` carries `exchReceiptSsboe/exchReceiptNsecs`. — [Rithmic/protos.json](/home/user/pfmon.com/Rithmic/protos.json)

### Inferences
**Rules that prevent look-ahead and repainting:**
- **Swing pivots:** a pivot high at bar *i* is only "confirmed" once bars *i+1…i+N* have closed lower (fractal/N-bar rule) or price has retraced by k×ATR (ZigZag-style). Store both `pivot_bar_time` and `confirm_time`. Setups may only use pivots whose `confirm_time ≤ now`. On charts, draw the pivot at its true location but mark it "known from confirm_time" (e.g., a dashed connector), so visual review does not credit the engine with hindsight.
- **Higher-timeframe bars:** use only `BarClosed` values for HTF context (e.g., weekly high/low = the last *completed* week). If the developing HTF bar is used, model it explicitly as `htf_developing{open, high_so_far, low_so_far, vol_so_far, as_of_seq}` and never as a final value. This is the engine-side equivalent of Pine's `[1]` + `lookahead_on`.
- **Profiles:** keep `profile_developing(session_id, as_of_seq)` separate from `profile_final(session_id)`. Prior-session and prior-week POC/VAH/VAL are final and safe. The current session's developing POC can migrate, so any setup using it must log the value at trigger time and accept that the "end-of-day POC" seen later will differ.
- **Fib grids:** a grid is identified by `(anchor_A pivot_id, anchor_B pivot_id)`. When a new confirmed pivot changes the anchor, emit a *new* grid version and invalidate (not mutate) the old one. Setups armed on the old grid either continue with logged levels or are cancelled according to a pre-declared rule. Cluster/confluence zones are computed from the set of active grid versions and logged with their member IDs.
- **Volume bars:** the bar closes on the trade that completes the volume. Signals are evaluated on that `BarClosed` event, never on a bar whose close is inferred later.
- **Never** let historical (seeded) bars and live bars differ in construction. Use the same builder code, and if seeding with server bars, cross-check that the last seeded bar matches the first live bars (or rebuild the overlap from recorded ticks).

**Decision record (write one per state transition, append-only, keyed by `setup_id`):**
`{strategy_version/git_sha, config_hash, setup_id, transition, event_seq, exch_ts, recv_ts, symbol/contract, last_trade, bbo, closed_bar_ids_by_tf, developing_bar_snapshot_by_tf, active_levels[{level_id, price, type, provenance, created_at}], swing_pivots_used[{pivot_id, price, pivot_time, confirm_time}], fib_grid_versions_used, profile_values_used{developing|final}, atr_by_tf, risk_state{day_pnl, trades_today, consec_losses, dd_buffer}, intended_order{type, price, stop, target, qty}, reason_codes[]}`.
- Visual audit tooling: (1) render the chart *as of* `event_seq`, with bars truncated at that point and only levels/pivots known then, next to the hindsight chart. (2) Annotate entries, exits and invalidations with `setup_id`. (3) Replay the event log through the engine and assert the same decisions are reproduced (a determinism test). A mismatch means look-ahead or nondeterminism.
- Use exchange-source timestamps for bar assignment, and store receive timestamps to measure feed latency (and stale-data alarms).

### Gaps
- No source was found that standardizes a "decision record" schema for retail automated futures systems. The schema above is a design recommendation, not an industry standard.
- Whether Rithmic server-built bars (`TimeBar`/`TickBar`) assign trades by exchange time or gateway receive time is not documented in the repo.

## 4. Execution: order types, brackets/OCO, trailing stops, slippage and queue position at levels, round-number clustering, partial fills, rejects/disconnects, exchange-native vs platform-simulated stops, CME price bands/velocity logic, pre-trade checks

### Takeaway
Use server-side brackets (Rithmic `RequestBracketOrder` 330 or Tradovate `placeOSO` / `startorderstrategy`) so a protective stop exists at the broker the moment the entry fills. Account for the fact that at CME, a "stop" is natively a stop-with-protection or stop-limit that can fail to fill through a gap, while trailing, OCO and bracket logic run on broker or platform servers, not at the exchange. Entries at levels should usually be limit orders offset a tick or two from the obvious round or level price, with hard pre-trade checks (price tolerance, max size, price bands, market state) and a time-based expiry on every working entry.

**CME exchange behavior**
- CME stop orders are stop-with-protection: activated "when the market trades at or through the stop trigger price and can only be executed within the protection range limit". The protection price is the trigger ± protection points, which "usually equal half of the Non-reviewable range", and any unfilled remainder rests at the protection limit. In iLink, stop orders are accepted only in Pre-Open, Open and No Cancel states, are returned as stop-limit on acceptance and as a limit once triggered, and a submitted tag 44-Price is ignored. — [CME Client Systems Wiki: Order Types for Futures and Options](https://cmegroupclientsite.atlassian.net/wiki/display/EPICSANDBOX/Order+Types+for+Futures+and+Options); [CME iLink Order Types](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457227032/iLink+Order+Types); [CME Education: Futures Order Types](https://www.cmegroup.com/education/courses/things-to-know-before-trading-cme-futures/futures-order-types)
- Market orders with protection: the protected range is "typically the current best bid or offer, plus or minus 50 percent of the product's Non-Reviewable Trading Range", and any remainder rests at the protection limit. A third-party example: with a 6-point NRR for ES, protection is 3 points (12 ticks). — [CME Market Integrity Controls (Client Systems Wiki)](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/46170793); [NexusFi: price banding and market protection](https://nexusfi.com/a/exchanges/price-banding-market-protection-mechanisms) (third-party; verify against current CME product files)
- Price banding rejects orders outside "Banding Reference Price ± Price Band Variation". Velocity logic monitors moves that go "too far, too fast" and temporarily suspends the market (and associated options) when an execution occurs outside a predefined point value within a predefined time. CME's Global Command Center "may temporarily expand certain risk parameters, such as price banding and Velocity Logic, during periods of volatility, such as the release of significant economic numbers." — [CME: Understanding Price Limits and Circuit Breakers](https://www.cmegroup.com/education/articles-and-reports/understanding-price-limits-and-circuit-breakers); [CME Market Integrity Controls](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/46170793)
- FIA price tolerance: "the maximum amount an individual order's limit price may deviate from a reference price… applied on orders generated from an automated trading system before the order is sent to the exchange… checks should be applied when a new order is submitted or when an existing order is modified." Maximum order size and maximum intraday position are also recommended pre-trade controls, the latter as a "speed bump to prevent accidental overtrading". — [FIA 2024 §1.1–1.3](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)
- FIA on cancel-on-disconnect (COD): COD is an exchange service that makes "a best-effort attempt to cancel all resting orders for the disconnected session". Brokers increasingly use COD on their own exchange connections, but pass-through cancellation when a *customer* disconnects from the broker "is typically unsupported, and the customer would need to contact the broker to manually cancel any working orders." — [FIA 2024 §1.4](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)
- FIA repeated automated execution limits: "the maximum number of times a strategy or identical order is filled and then re-enters the market without human intervention. After a configurable number of repeated executions, the strategy should be disabled until an authorized person re-enables it." — [FIA 2024 §3.2](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)
- Sierra Chart notes that some of its order types carry a `_CLIENT_SIDE` suffix (e.g., certain stop-limit and limit-if-touched variants), and that "Support for server-side brackets to exit a position entered through automated trading, is supported." This is an example of platform-simulated vs server-held order types. — [Sierra Chart: ACSIL Trading](https://www.sierrachart.com/index.php?page=doc/ACSILTrading.html)

### Inferences
**Entry order choice for level-based setups:**
- **Reversal/fade at a level** (e.g., weekly VAH + Fib cluster): use a limit order placed 1–2 ticks *in front of* the level (inside it toward the current price), not exactly at the round number or the obvious POC/Fib print where resting liquidity clusters. That improves fill probability when price "front-runs" the level. Accept that limit fills are adversely selected: a fill often means the level is being traded through. Measure "filled and immediately went against by ≥X ticks" as a fill-quality metric.
- **Breakout/acceptance setups:** use a stop-limit (trigger beyond the level, limit a few ticks further) rather than stop-market, to bound slippage. Log non-fills. A stop-limit missing the move is a cost the strategy must accept. At CME, a "stop-market" from the client becomes stop-with-protection at the exchange, or is held at the broker and sent as market-with-protection (exact Rithmic/Tradovate behavior unverified), so slippage is bounded by protection points but fills are not guaranteed.
- **Protective stops:** must be server-side (broker-held bracket legs), not local timers. Prefer bracket legs that are working orders at the broker, so they survive client disconnects. Treat trailing and break-even logic (Rithmic `breakEvenTicks`, `trailingStopTriggerTicks`; Tradovate `TrailingStop` / multibracket `trailingStop`) as broker-simulated. They work only while the broker's server is healthy and are not exchange-native.
- **Expiry on every entry:** Rithmic `cancelAfterSecs` / `cancelAtSsboe` and Tradovate `timeInForce:"GTD"` + `expireTime` act as a dead-man's switch. If the engine dies, stale entries expire on their own instead of filling hours later at a level that no longer matters.
- **Partial fills:** size bracket legs to the filled quantity (verify that Rithmic brackets release stop/target quantity in proportion to fills: `stopQuantityReleased`/`targetQuantityReleased` in `BracketUpdates` suggest they do). Decide in advance whether a partially filled entry gets its remainder cancelled at the bar close or the setup expiry, and never let the remainder sit unmanaged.
- **Rejects:** classify them (price band, RMS/limit, market state, malformed). A reject is a terminal state for that order. Never auto-retry the same intent more than once, and only after re-running all pre-trade checks. Repeated rejects trip the kill switch.
- **Disconnects:** on loss of the order connection, stop arming and do not send. On reconnect, reconcile before doing anything (§1). Because customer-side COD to the broker is typically unsupported (FIA), the bracket stop at the broker is the main protection while disconnected. Entries without brackets should never be used unattended.
- **Pre-trade checks (every new or modified order):** symbol/contract is the current front month; market state is Open (no `MarketMode` halt); price within `OrderPriceLimits` and within a self-imposed price tolerance of last/BBO (e.g., ≤ 1×ATR(1m) or ≤ N ticks); quantity ≤ max order size; resulting position ≤ max position; risk per trade ≤ budget; daily loss, trade count and consecutive-loss limits not breached; not inside a news blackout or session-end window; no duplicate working order for the same `setup_id`; data freshness (last tick < X seconds old, spread normal).
- **Message hygiene:** do not cancel/replace resting entries on every tick to "chase" a moving level. Update at most on bar close or with hysteresis (move only if the level moved ≥ 2 ticks). This keeps message rates low and avoids order patterns that could look like layering or spoofing (§5).
- **Mark orders as automated** (`manualOrAuto=AUTO` on Rithmic, `isAutomated:true` on Tradovate). The Tradovate spec explicitly requires this for non-human orders.

### Gaps
- Whether Rithmic `STOP_MARKET` and broker-side bracket stops are sent to CME as native stop-with-protection orders, or held on Rithmic servers and released as market or limit on trigger, is not stated in the repo docs. The same question applies to Tradovate `Stop`. The difference matters for gap risk and for behavior across the maintenance break.
- Current ES/MES/NQ/MNQ non-reviewable ranges, protection points and velocity-logic parameters were not retrieved from CME product files (CME's product file page needs a login or was not fetched).
- No authoritative data was found on retail queue position or fill probability at round numbers specifically. The "offset by 1–2 ticks" advice is practitioner convention, not a sourced statistic.

## 5. Risk management for unattended automation (per-trade risk, sizing micros vs minis, daily/trade-count/consecutive-loss limits, news blackouts, session filters, kill switch, heartbeat/disconnect auto-flatten, prop-firm trailing drawdown) and regulatory notes (CME Rule 575, spoofing)

### Takeaway
Use defense in depth: engine-level limits (which halt new entries) sit inside broker-level limits (Rithmic RMS / Tradovate auto-liq, which flatten), which sit inside prop-firm rules. All of them must be readable by the engine so it stops well before a broker or firm threshold is hit. ### Inferences
**Recommended limit hierarchy** (engine thresholds strictly tighter than broker and firm thresholds):
1. **Per trade:** risk budget in R. Stop distance = max(structure-based stop to beyond swing or level + buffer, k×ATR(entry TF)). `qty = floor(risk_$ / (stop_ticks × tick_value))`. If qty < 1 micro, *skip the trade* rather than widening risk. Tick values from standard CME multipliers (verify on CME specs): MES $1.25/tick (0.25 pt × $5), ES $12.50, MNQ $0.50 (0.25 × $2), NQ $5.00. One mini equals 10 micros, so micros give 10× finer sizing granularity. That matters when structure stops on 240m/daily setups are 20–60+ ES points.
2. **Per day:** max loss (e.g., 2–3R or a fixed $ well inside the broker/firm daily limit), max trades (e.g., 3–5), max consecutive losses (e.g., 3) → stop for the day. Add a profit-lock option (Tradovate `dailyProfitAutoLiq` exists natively). Also apply FIA's "repeated automated execution" limit: N fills of the same setup type without human review → disable.
3. **Per week/account:** weekly loss limit (Tradovate `weeklyLossAutoLiq`). For prop accounts, compute `distance_to_liquidation = current_balance − autoLiqThresholdCurrentValue` (Rithmic) or the trailing-max-drawdown equivalent (Tradovate `trailingMaxDrawdown`, mode EOD vs RealTime). Block entries whose worst-case loss (stop + slippage allowance + open P&L giveback) would breach that distance minus a buffer. With **RealTime** trailing, open profits raise the peak, so unrealized gains given back count against the drawdown. With **EOD**, only the closing balance trails. The engine must model whichever mode the firm uses.
4. **Session/time filters:** no new entries in the first N minutes after the Globex reopen (17:00 CT) or RTH open (08:30 CT) unless the setup is designed for them. No entries within N minutes of the 15:00 CT RTH close or the 16:00 CT maintenance start. Flatten-by time for intraday setups (Rithmic `stopMarketAtSsboe` / `targetMarketAtSsboe`, Tradovate `flattenTimestamp` as a broker-side backstop).
5. **News blackouts:** keep a machine-readable calendar (FOMC from federalreserve.gov, NFP/CPI from bls.gov). Block new entries from T−5/10 min to T+15/30 min, optionally tighten or flatten intraday positions before tier-1 events, and widen expectations for slippage (CME may widen bands then).
6. **Kill switch (layered, per FIA):** (a) an in-app button/CLI/hotkey that cancels all (`RequestCancelAllOrders` / cancel each), flattens (`RequestExitPosition` / `/order/liquidatepositions`), and disables strategy arming until a manual reset. (b) An *out-of-process* watchdog that can do the same if the engine hangs. (c) A broker-level backstop (Rithmic RMS loss limit / auto-liquidate, Tradovate auto-liq) set slightly beyond the engine's own limits. (d) A documented manual fallback (broker phone desk / R|Trader / Tradovate web) for when the API path is down.
7. **Heartbeats and watchdogs:** honor the server-provided Rithmic `heartbeatInterval`. Answer Tradovate `h` frames with `[]`. Raise "stale data" if no tick arrives within X seconds during liquid hours, or if BBO is crossed or the spread is abnormally wide (FIA 3.1). Raise "stale order channel" if no order-plant traffic or heartbeat response arrives within 2× the interval. On stale market data, block entries and keep the brackets. On a stale order channel, do not try to place new orders: alert loudly (push/SMS), rely on server-side brackets, and reconcile on reconnect. "Auto-flatten on disconnect" is only possible if the *order* path is still alive (e.g., market data died). The design should therefore assume flattening may be impossible during an outage, which is why every position must carry a server-side stop.
8. **Token/session hygiene:** renew Tradovate tokens before `expirationTime` (`/auth/renewaccesstoken`). Handle Tradovate `shutdown` events and Rithmic `ForcedLogout` as kill-switch triggers. Ensure no other app uses the same Tradovate login, given the one-connection limit.

**Rule 575 / anti-spoofing design rules for the bot:**
- Only submit orders the strategy genuinely intends to have filled. Never place "probe" or decoy orders, and never stack multiple resting orders to signal size.
- Rate-limit modifications (bar-close or hysteresis updates, §4). Cap messages per second and per minute in the order manager.
- Detect runaway loops (e.g., > N order messages in M seconds, or the same intent re-sent) → kill switch. RA2608-5's new "disruptive messaging" examples make this more important. Even a buggy, non-manipulative loop could fall under the "reckless" standard.
- Avoid placing or cancelling orders near the settlement/closing period for any reason other than genuine execution (RA2608-5 covers closing-period conduct).
- Log `reason_code` on every cancel (setup invalidated, expiry, risk veto), so a pattern of cancels can be explained if questioned.

**Prop-firm practicality:** Topstep's VPS ban and its API's exclusion from Live Funded accounts mean a cloud-hosted bot is not allowed there. The Rithmic "TopstepTrader" system in `systems.js` may be legacy, given Topstep's move to TopstepX (unverified). For Apex and others, get written rules from the firm. The repo's prop-firm Rithmic systems imply the user may trade prop accounts through R|Protocol, but connectivity is not the same as permission.

## 6. Validation without backtesting: forward testing in simulation, signal-only mode, replay, visual review checklists, minimum sample sizes and simple statistics, and the difference between "not optimizing" and "not testing"

### Takeaway
Not backtesting does not mean not testing. The user can run a staged forward-validation protocol with fixed, version-tagged rules: signal-only with chart annotations → simulated execution (Rithmic Paper Trading / Tradovate demo) → deterministic replay rehearsal of chosen days (Tradovate Market Replay or the engine's own recorded-tick replay) → minimum-size live (1 micro). Go/no-go is decided on pre-declared statistics (expectancy in R with its standard error, MAE/MFE, slippage, and the user's visual "agree/disagree" rate). Changing a rule starts a new sample.

### Cited Findings
- FIA: "Organizations should have a process for testing trading software and infrastructure before any new system, new versions or updates are released to the production environment". Exchange-based conformance testing should be repeated "when material changes have been made to previously approved exchange-facing software interfaces." — [FIA 2024 §5](https://fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)
- Sierra Chart advises: "thoroughly test your trading study through backtesting and in Sierra Chart Trade Simulation Mode with live data." `sc.SendOrdersToTradeService` / global Trade Simulation Mode toggle simulated vs. real routing. — [Sierra Chart: ACSIL Trading](https://www.sierrachart.com/index.php?page=doc/ACSILTrading.html)
- Tradovate Market Replay simulates "a given timeframe as if it were happening live" at 0–400% speed, using a throwaway replay account. `/account/resetdemoaccountstate` exists for demo accounts. — [Tradovate/openapi.json](/home/user/pfmon.com/Tradovate/openapi.json)
- The repo's Rithmic config includes the `Rithmic Paper Trading` system, and an unofficial client identifies "Rithmic Test" as the pre-approval test system. — [Rithmic/config/systems.js](/home/user/pfmon.com/Rithmic/config/systems.js); [rithmic-rs config.rs](https://docs.rs/crate/rithmic-rs/latest/source/src/config.rs)
- NinjaTrader Tick Replay "was NOT designed to provide accuracy in backtesting concerning order fills and execution". Replay and sim fills are therefore optimistic relative to live queue position. — [NinjaTrader: Developing for Tick Replay](https://static.ninjatrader.com/support/helpGuides/nt8/developing_for__tick_replay.htm)
- Topstep recommends testing on a Practice Account before running automation in a Combine. — [Topstep: TopstepX API Access](https://help.topstep.com/en/articles/11187768-topstepx-api-access)

### Inferences
**Staged protocol (each stage has entry and exit criteria; rules frozen per `strategy_version`):**
- **Stage 0, plumbing (1–2 weeks, sim):** connectivity, reconnect, heartbeat, restart-reconcile, kill switch, and bracket placement/modification on Rithmic Paper Trading or Tradovate demo. Force failures deliberately (kill the process mid-trade, drop the network, send an invalid price, simulate a reject) and verify the outcomes. This is engineering testing and involves no strategy judgment.
- **Stage 1, signal-only (minimum ~4–6 weeks, or ≥30–50 signals per setup type, whichever is later):** the engine generates setups and hypothetical orders, writes decision records, and draws annotations, but sends nothing. The user reviews each signal visually with a fixed checklist: (1) Were the levels the engine used actually visible at the time (as-of chart)? (2) Was the swing confirmed before use? (3) Does the HTF context match the user's discretionary read? (4) Would the user have taken it (yes/no/maybe)? (5) Was the invalidation rule correct? (6) Did the hypothetical fill price assume a fill that probably would not have happened (price only touched the limit)? Track the **agreement rate** and the **false-trigger categories**.
- **Stage 2, sim execution (≥ 50–100 trades total):** real orders on paper/demo. Measure fills vs. hypothetical prices, slippage on stops, partial fills, rejects, and timing. Sim fills are optimistic (queue position is not modeled faithfully), so for limit entries count a fill only if price traded *through* the limit by ≥1 tick in a parallel "conservative" column.
- **Stage 3, replay rehearsal (targeted):** replay specific stress days (FOMC days, NFP, roll week, holiday half-days, gap opens) through Tradovate Market Replay or the engine's own recorded ticks. The aim is to verify behavior (blackouts, flattening, roll switch), not to measure edge. Replaying fixed rules without tuning is rehearsal, not optimization.
- **Stage 4, minimum live (1 MES/MNQ):** only after Stage 1–2 criteria pass. Same stats, plus a live-vs-sim slippage comparison.

**Simple statistics to compute per setup type and in aggregate (in R multiples):**
- Win rate *p*, average win *W* (R), average loss *L* (R), expectancy `E = p·W − (1−p)·L` (≈ mean R per trade), profit factor, max consecutive losses, max drawdown in R, average MAE and MFE in R (and the distribution, to check whether stops sit beyond normal noise and whether targets are realistic), average slippage in ticks (entry and stop separately), and fill rate for limit entries.
- **Sample-size intuition:** the standard error of mean R is `SE ≈ sd(R)/√n`. With a typical sd(R) of about 1.0–1.5R for 1R-stop / 1.5–2R-target systems, n=30 gives SE ≈ 0.18–0.27R and n=100 gives SE ≈ 0.10–0.15R. Showing E = +0.2R is above zero with about 95% one-sided confidence needs roughly `n ≈ (1.645·sd/E)² ≈ 70–150` trades. Thirty trades can reject "badly broken" but cannot confirm a modest edge. Set the decision rule in advance, e.g., "go live at 1 micro if after ≥50 sim trades E > 0 with lower 80% bound > −0.1R, slippage within budget, and agreement rate ≥ 80%. Abort if E < −0.3R after 30 trades or any risk-control failure occurs."
- Segment results by session (RTH/ETH), timeframe of the setup, and level type (profile vs. Fib vs. swing) only to *diagnose*. With small n, segment-level differences are mostly noise. Do not use them to tweak parameters mid-sample.

**Not optimizing vs. not testing:** "not optimizing" means parameters are set from discretionary experience *before* data collection and are not tuned to the sample. "Not testing" would mean going live with no evidence. Forward testing with frozen rules is legitimate out-of-sample evidence. Every rule or parameter change increments `strategy_version`, and the stats restart (or are reported separately), which prevents slow, unacknowledged curve-fitting through repeated small tweaks.

- No authoritative source was retrieved on minimum forward-test sample sizes for discretionary-style futures systems. The numbers above are standard statistical reasoning (standard error of a mean), not citations.
- Whether Rithmic Paper Trading supports R|Protocol API order routing for the user's credentials (vs. only R|Trader) remains unverified, given the conflicting secondary claims (§2).
- Fidelity of sim fills on Rithmic Paper Trading and Tradovate demo (queue modeling, stop slippage) is not documented in the sources found.

## 7. Platform alternatives if not fully custom: NinjaTrader 8, Sierra Chart, TradingView (+ TradersPost/PickMyTrade), Quantower, MotiveWave, ATAS — pros/cons for volume bars, volume profile, multi-timeframe

### Takeaway
For this strategy family (volume bars, multi-week volume profiles, multi-timeframe swings, server-side brackets), NinjaTrader 8 and Sierra Chart are the strongest off-the-shelf automation hosts. Both support volume bars, multi-series up to weekly, per-price bid/ask volume, and server-side brackets, and both have explicit historical-vs-realtime processing rules. TradingView + webhook bridges are the fastest to prototype but the weakest for unattended safety: bar-close logic, webhooks that can fail or arrive late, no retries at the bridge, and a 1-minute minimum at TradersPost. ATAS, MotiveWave and Quantower are viable but less documented for automation in what was found. A custom build on the repo's Rithmic layer gives the most control and best fits the pfmon journal integration, but carries all the engineering risk.

### Cited Findings
**NinjaTrader 8**
- `AddDataSeries()` supports `Tick, Volume, Range, Second, Minute, Day, Week, Month, Year` (plus custom bar types). It must be called "ONLY" in `State.Configure` with hardcoded arguments ("Adding series dynamically is not reliable", which can produce "Unable to load bars series"). `BarsInProgress` identifies which series triggered `OnBarUpdate()`. — [NinjaTrader AddDataSeries()](https://static.ninjatrader.com/support/helpGuides/nt8/adddataseries.htm)
